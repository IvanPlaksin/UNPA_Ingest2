## 2. RuntimeEngine Flow

### 2.1 Entry Point

```javascript
async execute(dag, inputData = {}, executionConfig = {})
```

- **dag**: `{ nodes: Node[], edges: Edge[] }` — supports both ReactFlow and AOPEG format
- **inputData**: Object passed to entry nodes
- **executionConfig**: `maxConcurrency`, `schedulingStrategy`, `errorStrategy`, `enableValidation`, etc.

### 2.2 Execution State Machine

```
CREATED → INITIALIZING → READY → RUNNING → (COMPLETED | FAILED | WAITING | TIMED_OUT)
```

### 2.3 Execution Phases

1. **VALIDATION**: GraphValidator validates DAG structure, attempts auto-fix
2. **INITIALIZATION**: Tool registration, PortManager, DataFlowManager, ExecutionContext, TopologicalScheduler
3. **INPUT INJECTION**: Finds entry nodes, sets inputData on `_input` port
4. **EXECUTION**: Scheduler starts (Kahn's algorithm), global timeout
5. **COMPLETION**: Returns based on scheduler status (COMPLETED/FAILED/WAITING)

### 2.4 No Graph-Level Type Branching

**There is NO explicit dialog vs. business graph type branching.** All branching is dynamic via:
- Node output `branch` field matching edge `label` field
- Semantic label matching (TRUE_LABELS / FALSE_LABELS)
- Error strategy: FAIL_FAST vs CONTINUE_ON_ERROR

### 2.5 WAIT_FOR_INPUT Flow

1. **Executor returns** `{ status: 'WAIT_FOR_INPUT', resume_token, expected_inputs, prompt, choices }`
2. **NodeRunner intercepts** → wraps in `AsyncSignalContract`
3. **Scheduler** transitions node to `WAITING_INPUT`, saves checkpoint
4. **Client** renders form via `waitingNodeToFormDefinition()`
5. **User submits** → `POST /runtime/signal/resume` with `{ token, payload, actorId }`
6. **SignalOrchestrator** validates token, resolves signal
7. **Scheduler** re-enqueues node, NodeRunner re-executes with payload
8. **Execution continues** downstream

### 2.6 Tool ID Resolution

```javascript
const toolId = node.executorType || node.data?.toolId || node.data?.tool || node.data?.kind
```

No graph-level type check exists. Type-dependent behavior is only at the node level.

## 3. Port System & Forms

### 3.1 Schema Source

Every AOPEG executor defines `parameterSchema` (JSON Schema):

```javascript
// plugin-base.ts
abstract readonly parameterSchema: Record<string, unknown>;
```

### 3.2 Schema Flow

```
AOPEG Executor (parameterSchema)
  → AOPEGAdapter (maps to inputSchema)
  → PortManager (registers input ports)
  → NodeRunner (validates input)
```

### 3.3 Form Generation

**File:** `mcp/src/components/FlowDesk/waitingNodeToForm.js`

`waitingNodeToFormDefinition(waitingNode)` converts WAIT_FOR_INPUT data to FormDefinition:
- Choices → `select` field
- Text input → `textarea` field
- Produces `{ id, name, sections: [{ id, fields: [...] }] }`

### 3.4 Form Rendering

```
FormRenderer → FormSection → FormField → Field Component (TextField, SelectField, etc.)
```

**Hooks:**
- `useFormState` — manages formData, setFieldValue
- `useFormValidation` — field-level + form-level validation
- `useDisplayConditions` — conditional field visibility

### 3.5 Validation

1. **Field-level** (on change): required check + custom predicates
2. **Form-level** (before submit): full validation pass
3. **Predicate evaluator**: `evaluatePredicate(expression, context)` — supports JS-like expressions

### 3.6 Submit Flow

- **EMBEDDED mode**: parent component handles `onSubmit` callback
- **STANDALONE mode**: auto-resumes via `POST /runtime/signal/resume`

## 6. Gap Analysis

### 6.1 Missing Properties on GraphDefinition

| Gap | Description | Impact |
|-----|-------------|--------|
| **No `graphType` property** | `CatalogEntry.type` is informal (atomic/tool/business/composite/template) — no formal enum | Cannot differentiate EXECUTABLE vs STRUCTURAL vs CONSTRAINT |
| **No `graphDimension`** | No EXECUTION/DATA/GOVERNANCE classification | No type-aware routing in RuntimeEngine |
| **No `structuralGraphId`** | WAIT_FOR_INPUT nodes can't reference a STRUCTURAL graph | Forms generated from executor schema, not from reusable graph definitions |

### 6.2 Type-Dependent Behavior Without Stored Type

| Area | Current Behavior | Desired Behavior |
|------|-----------------|------------------|
| RuntimeEngine.execute() | Accepts any DAG blindly | Should reject non-executable types |
| CatalogEntry creation | No type validation | Should validate against formal enum |
| Graph search/filter | Filters by informal `type` string | Should filter by `graphType` + `graphDimension` |
| Form generation | Inline from executor parameterSchema | From referenced STRUCTURAL graph |

### 6.3 Validation Gaps

- No check that STRUCTURAL graphs contain only FIELD/OBJECT/ARRAY nodes
- No check that CONSTRAINT graphs reference valid STRUCTURAL graphs
- No check that COMPOSITE graphs reference valid sub-graphs
- No STORABLE → STRUCTURAL conformity check

### 6.4 CatalogEntry.type vs. GraphType

**Current `CatalogEntry.type` values:** `'atomic'`, `'tool'`, `'business'`, `'composite'`, `'template'`

**Proposed `graphType` values:** `EXECUTABLE`, `TEMPLATE`, `COMPOSITE`, `PROCESS`, `STRUCTURAL`, `STORABLE`, `PROJECTION`, `CONSTRAINT`, `VALIDATION`, `EVENT`

**Migration mapping:**
| Current type | → graphType |
|-------------|-------------|
| `atomic` | `EXECUTABLE` |
| `tool` | `EXECUTABLE` |
| `business` | `EXECUTABLE` (subType: `business`) |
| `composite` | `COMPOSITE` |
| `template` | `TEMPLATE` |

## 7. Migration Risk Assessment

### 7.1 Graphs Requiring Migration

All 15+ existing graphs need `graphType` property added. All currently map to `EXECUTABLE` or `COMPOSITE`.

### 7.2 Breaking Changes Potential

| Risk | Level | Mitigation |
|------|-------|------------|
| Existing `CatalogEntry.type` consumers | **MEDIUM** | Keep `type` as backward-compat alias, add `graphType` alongside |
| RuntimeEngine type gates | **LOW** | Default to `EXECUTABLE` for graphs without graphType |
| GXE UI graph creation | **MEDIUM** | UI must be updated to set graphType on new graphs |
| Seed scripts | **LOW** | Update all seed scripts to include graphType |
| Graph search APIs | **MEDIUM** | Add graphType filter, keep type filter for backward compat |

### 7.3 Safe Migration Strategy

1. Add `graphType` as **optional** property (Phase 1)
2. Set default `'EXECUTABLE'` on all existing graphs (Phase 1.2)
3. Make `graphType` **required** for new graphs only (Phase 1.4)
4. Gradually enforce on existing graphs (Phase 2)
5. Add runtime type checks with fallback to EXECUTABLE (Phase 3)
